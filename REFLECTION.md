# Reflection

The hardest part of this capstone was two things I'd never done before: writing automated tests, and debugging mobile Lighthouse performance scores.

I'd never written a test before this project, so the first Jest run — nine failures, all pointing to a `scrollTo is not a function` error I didn't recognize — was genuinely intimidating. I didn't know what jsdom was, why my component code (which worked fine in the browser) was "broken" in a test, or how mocking worked. Learning that a test environment isn't a real browser, and that you have to explicitly tell it how to fake things like `scrollTo` or `IntersectionObserver`, was a real shift in how I think about my own code — it forced me to actually understand what each piece of a component depends on, rather than just knowing that it works when I click around it myself.

The Lighthouse mobile score was its own kind of hard. My desktop score was 99 from the very first run, so I assumed mobile would be close behind — instead it came back at 73, and I didn't understand why the same code could score so differently. Digging into the diagnostics (Total Blocking Time, unused JavaScript, long main-thread tasks) and slowly tracing them back to real causes — the chatbot's JS loading eagerly, Framer Motion's full bundle running everywhere, client widgets hydrating all at once on page load — taught me that "it works" and "it performs well on a real phone" are two completely different bars, and that mobile CPUs are simulated as much slower on purpose because that gap is real for a lot of users.

If I could do this capstone again, I'd write tests alongside each component as I built it, instead of leaving all of them until the very end. Writing them afterward meant I had to re-learn what each component was supposed to do from scratch by reading old code, which took longer than if I'd written the test right after building the feature, while the logic was still fresh in my head.

What surprised me most was just how large the gap between desktop and mobile performance can be from the exact same codebase — and how much of that gap came down to JavaScript that wasn't even being used yet (like the chatbot's code loading before anyone opened the chat). I went into this thinking performance was mostly about image sizes; I came out of it understanding that unused, eagerly-loaded JavaScript is often the bigger, less visible cost.
